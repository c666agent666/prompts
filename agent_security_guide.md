# Comprehensive Guide to Securing Coding Agents

When working with autonomous coding agents (like AutoGen, LangChain, SWE-agent, or custom scripts), their ability to write and execute code introduces significant security risks—especially **shell-escaping artifacts** and command injections. 

This guide provides a "bells and whistles" setup for a defense-in-depth architecture. We will cover environment isolation, secure tool design, human intervention layers, and automated static analysis.

---

## Layer 1: Environment Isolation (The Sandbox)

Never run a coding agent directly on your host operating system. If the agent generates a destructive shell command (e.g., `rm -rf /` or malicious payloads), it should only destroy a disposable environment.

### 1.1 The Docker Sandbox setup
Create a dedicated `Dockerfile` for your agent's workspace. This file ensures the agent runs as a non-root user and restricts access to the host.

**`Dockerfile`**
```dockerfile
FROM python:3.11-slim

# Create a non-root user
RUN useradd -m -s /bin/bash agentuser

# Set working directory
WORKDIR /app

# Copy agent dependencies (if any)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Give the agentuser ownership of the workspace
RUN chown -R agentuser:agentuser /app

# Switch to the non-root user
USER agentuser

# Default command keeps the container alive for the agent to use
CMD ["tail", "-f", "/dev/null"]
```

### 1.2 Running the Sandbox
Start the container with a restricted file mount so the agent can only access specific project files.

```bash
docker build -t agent-sandbox .
docker run -d --name agent_workspace -v $(pwd)/project_files:/app/project_files agent-sandbox
```
*Note:* The agent should execute its commands *inside* this container using `docker exec`.

## Layer 2: Safe Tooling (Prevention)

The root cause of shell-escaping artifacts is passing raw, LLM-generated strings directly into a shell interpreter. You must remove generic shell access and provide strictly typed tools.

### 2.1 Avoid `shell=True`
If you are building your own agent tools in Python, **never** use `shell=True`. Use `shell=False` (the default) and pass arguments as a list. This bypasses the shell entirely, making shell-escaping artifacts harmless because special characters (like `;` or `&`) are treated as literal strings.

**Unsafe Implementation (DO NOT USE):**
```python
import subprocess

def bad_execute(command: str):
    # DANGEROUS: If command is "ls; rm -rf /", it executes both.
    subprocess.run(command, shell=True) 
```

**Secure Implementation:**
```python
import subprocess
import shlex

def safe_execute(command_string: str):
    # shlex.split safely parses the string into a list
    # e.g., "git commit -m 'hello; world'" -> ['git', 'commit', '-m', 'hello; world']
    args = shlex.split(command_string)
    
    try:
        # shell=False ensures artifacts are not interpreted as commands
        result = subprocess.run(args, shell=False, capture_output=True, text=True, check=True)
        return result.stdout
    except subprocess.CalledProcessError as e:
        return f"Error: {e.stderr}"
```

## Layer 3: Human-in-the-Loop (HITL) Interceptor

Even with safe tooling, you might want final approval over what the agent executes. Implementing a HITL interceptor acts as a manual safety net.

### 3.1 Python Interceptor Middleware
Wrap your agent's execution tool with a prompt that pauses execution until you press `Y`.

```python
def hitl_execute_tool(tool_name: str, parameters: dict):
    print(f"\n[⚠️ AGENT ACTION PENDING]")
    print(f"Tool: {tool_name}")
    print(f"Parameters: {parameters}")
    
    user_input = input("Allow execution? (Y/n): ").strip().lower()
    
    if user_input in ['y', 'yes', '']:
        print("Execution approved.")
        # Call actual tool here
        return "Tool executed successfully."
    else:
        print("Execution denied.")
        return "Action blocked by user."
```

## Layer 4: Automated Detection with Semgrep

To search for and correct shell-escaping artifacts in the code the agent *writes*, use Semgrep. It is a fast Static Application Security Testing (SAST) tool.

### 4.1 Setup Semgrep
Install Semgrep on your host machine:
```bash
# macOS
brew install semgrep

# Linux/Windows (via pip)
python3 -m pip install semgrep
```

### 4.2 Scan the Agent's Output
Run Semgrep against the directory where your agent saves its code (e.g., `project_files`). Use the built-in command-injection ruleset.

```bash
semgrep --config "p/command-injection" ./project_files
```

### 4.3 Custom Rule for Escaping Artifacts
You can write a custom Semgrep YAML rule to look for suspicious escaping patterns (like double-escaped variables) in shell scripts generated by the agent.

**`detect_artifacts.yml`**
```yaml
rules:
  - id: suspicious-shell-artifact
    pattern-regex: (\\\$)
    message: "Found a potential shell-escaping artifact (\$). Verify if this was intended to be a literal string or if escaping failed."
    languages:
      - bash
    severity: WARNING
```
Run it via: `semgrep --config detect_artifacts.yml ./project_files`

## Layer 5: AI-on-AI Code Review (The Security Agent)

Create a secondary, specialized LLM agent whose sole job is to review the code generated by your primary coding agent.

### 5.1 Security Reviewer System Prompt
Initialize a new LLM instance with the following strict system prompt:

> **System Prompt: Security Validator Agent**
> You are a senior security engineer. Your sole task is to review code written by another AI agent and identify shell-escaping artifacts, command injection vulnerabilities, and dangerous executions (e.g., `eval()`, `shell=True`, `system()`).
> 
> **Instructions:**
> 1. Read the provided code carefully.
> 2. If you find ANY unescaped variables passed into system commands, flag them.
> 3. If you find lingering escape characters (e.g., `\"`, `\$`) that indicate a parsing error, flag them.
> 4. If the code is secure, respond ONLY with "PASS".
> 5. If the code is insecure, respond with "FAIL", specify the exact line number, and provide the corrected code.

Pass the output of your coding agent directly to this Security Validator Agent before allowing the code to be saved or executed.
